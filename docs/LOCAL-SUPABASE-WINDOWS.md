# Local Supabase Stack — Windows

This guide runs a **local** Supabase development stack for OKEngine. It uses the repo's migration files and Supabase CLI; it does not link to or change a hosted Supabase project. Optional local Google/GitHub Auth setup is documented separately in [LOCAL-SUPABASE-OAUTH-WINDOWS.md](./LOCAL-SUPABASE-OAUTH-WINDOWS.md); no OAuth credentials are needed for email/password testing.

## What will run

The requested local services are enabled in `supabase/config.toml`:

- PostgreSQL **15** on host port `54322` (the migrations require PostgreSQL 15+).
- Supabase Auth, needed for the local Supabase auth schema/functions used by the RLS migrations.
- Supabase Storage, with the image-transformation service disabled. The migrations create the private `workspace-files` bucket with the repository's 10 MiB limit.
- Supabase Edge Runtime.
- The Supabase API gateway and PostgREST. These are required plumbing: OKEngine's Supabase client calls `/rest/v1`, `/auth/v1`, `/storage/v1`, and `/functions/v1` through the local API URL. They cannot be removed while using those local APIs.

Studio, the local SMTP mail-catcher, Realtime, Analytics, the DB pooler, Storage's S3 protocol/vector/analytics extensions, and image transformations are disabled. The exact helper-container names can vary with Supabase CLI versions.

**Resource-limit distinction:** this config minimizes the services/containers. Supabase CLI's `config.toml` does not provide dependable per-container CPU/RAM caps. Set an overall budget in **Docker Desktop → Settings → Resources**; per-container limits would require a separately managed Compose setup and are not covered by this script.

## Windows prerequisites

1. Install and start Docker Desktop. Use the WSL 2 backend and Linux containers; wait until Docker Desktop reports its engine is running.
2. Install the Supabase CLI and ensure `supabase --version` works in PowerShell. One common Windows installation is Scoop:

   ```powershell
   scoop bucket add supabase https://github.com/supabase/scoop-bucket.git
   scoop install supabase
   ```

3. Install the repository's Node dependencies (`npm ci`) from the repository root.

## Start the stack

From the repository root in PowerShell:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\supabase-local.ps1 -Action up -WriteAppEnv
```

The script checks Docker and the Supabase CLI, starts the local stack, applies pending local migrations, and prints the service status. `-WriteAppEnv` writes a `.env.local` using the **local keys generated by Supabase CLI** plus fresh development-only application secrets. `.env.local` is already ignored by Git. For safety, the script refuses to overwrite an existing `.env.local`; back it up or merge the local values manually if you already have one.

Then start OKEngine:

```powershell
npm run dev
```

Open `http://localhost:3000`.

To manage the local stack:

```powershell
.\scripts\supabase-local.ps1 -Action status
.\scripts\supabase-local.ps1 -Action down     # stops containers; keeps local data
.\scripts\supabase-local.ps1 -Action reset    # destructive; asks for RESET first
```

`reset` drops and recreates the **local** database and reapplies migrations. Do not use it if you need to keep local data. `down` stops the services without intentionally deleting their volumes.

## Local endpoints and keys

| Purpose | Local endpoint / value |
| :--- | :--- |
| Supabase API gateway | `http://127.0.0.1:54321` |
| PostgreSQL | `127.0.0.1:54322`, database `postgres`, user `postgres` |
| Auth API | `http://127.0.0.1:54321/auth/v1` |
| Storage API | `http://127.0.0.1:54321/storage/v1` |
| Edge Functions API | `http://127.0.0.1:54321/functions/v1` |

Use the generated `DB_URL` and `API_URL`, plus the local public/server keys from `supabase status -o env`. Depending on CLI version, those keys may be named `ANON_KEY` / `SERVICE_ROLE_KEY` or `PUBLISHABLE_KEY` / `SECRET_KEY`; the setup script normalizes either pair to OKEngine's names (`SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`). It maps `DB_URL` and `API_URL` to `DATABASE_URL` and `SUPABASE_URL`. These are **local development credentials**, not your hosted-project credentials.

The service-role key is privileged even in local development: keep it in the ignored `.env.local`, never put it in browser code, Git, or chat. Do not paste hosted Supabase keys here. The local CLI can generate the local keys without them.

## Application integration and local limits

The application now has a Supabase-backed path for the core integration:

- `/api/auth/signup`, `/api/auth/login`, password recovery, and logout use Supabase Auth through request-scoped SSR clients. Auth sessions are stored in HttpOnly cookies; the login form's “Remember me” preference keeps the browser session cookie for 30 days, while leaving it unchecked uses a browser-session cookie. A database trigger maps new Auth UUIDs to `public.users`; the `provision_initial_workspace()` RPC creates an owner workspace without trusting a client-supplied user or workspace ID.
- Optional Google/GitHub sign-in uses the same Auth UUID/callback/workspace-provisioning path. Each provider stays hidden unless its complete server-side client ID and secret are locally configured; this adds no Supabase services. See [LOCAL-SUPABASE-OAUTH-WINDOWS.md](./LOCAL-SUPABASE-OAUTH-WINDOWS.md) for provider-console setup, local env, restart, and verification steps. Never paste provider secrets in chat or commit them.
- Existing custom-password profiles are **not** linked to Auth users by email. Import/backfill legacy accounts through a separately verified migration before expecting those accounts to sign in; no passwords or account secrets are copied automatically.
- The browser receives only a safe `/api/auth/session` profile/workspace projection; Auth access and refresh tokens remain in HttpOnly cookies. Login, signup, callback, password recovery/reset, and logout use Supabase Auth.
- Tenant API reads and writes use the incoming user's Supabase JWT so Postgres RLS evaluates `auth.uid()`. The process-global service-role client is restricted to operation-specific system-repository methods and is never a fallback for user queries. Anonymous chat can retrieve only RLS-approved `everyone` collections; invalid custom bearer/HMAC identities are rejected.
- Private `workspace-files` uploads are limited by the Storage bucket to 10 MiB and Markdown, plain text, or PDF. Uploads create a pending metadata row, upload the object, and finalize through a narrow permission-checked RPC. Downloads use short-lived signed URLs; deletion checks both Storage and row permissions.
- Scope boundary: the legacy dashboard components (`CollectionsView`, embed/settings/conversation views, and the client `store`) still use the local demo store and are **not yet connected** to Postgres CRUD. Supabase-mode workspace routes are gated away from those demo-backed pages and show a tenant-backed overview of RLS-visible collections, documents, and private files; the overview supports private upload/download. The Auth/session, chat retrieval, billing authorization, and file APIs are server-backed, but the legacy `UploadDropzone` and CRUD/editing views remain unconnected. Do not treat successful login as proof that every dashboard page has been migrated.
- The current Supabase chat route deliberately rejects the legacy custom HMAC embed token. Anonymous public RLS retrieval works, but protected embed identities and embed-bound collection narrowing have not yet been bridged to Supabase Auth/RLS. Do not enable third-party embeds in Supabase mode until that boundary is implemented and tested.
- The Edge Runtime is enabled, but this checkout does not yet contain an application-owned Edge Function. It is available for later functions without enabling Studio, Realtime, Analytics, or a mail-catcher.
- Migrations create the schema, RLS, Auth profile trigger, workspace provisioning RPC (including a private starter collection), and private Storage policies. They do **not** import OKEngine's TypeScript demo documents or demo workspaces into PostgreSQL. The public demo and legacy dashboard code still have client-side demo data, but the workspace layout hides those legacy pages in Supabase mode and loads a separate tenant-backed overview instead. Server API routes in enforced Supabase mode do not silently fall back to seed arrays.
- Local Auth email confirmations are disabled so signup can be tested without an SMTP container. The password-recovery flow itself is wired to the Auth callback, but delivery of recovery email requires an SMTP provider/configuration; the local stack config intentionally leaves SMTP disabled.
- `scripts/supabase-local.ps1 -Action up` applies pending migrations with `supabase migration up --local`. `supabase db reset` is destructive. `supabase db push` targets a **linked hosted project**, not this local-only workflow.
- The `npm run migrate` package script still points to `src/lib/migrate.ts`, which is absent in this checkout. Use the Supabase CLI commands in this guide instead.

## Verify the integration

Install dependencies once from the repository root:

```powershell
npm ci
```

Run the **fast** security and route-contract suite. It requires Node/npm only—no Docker, Supabase CLI, local `.env.local`, or provider credentials:

```powershell
npm run test:auth-fast
```

Run the **local-stack runtime** suite with one command:

```powershell
npm run test:auth-local
```

The local command checks Docker, the Supabase CLI, the checked-in service config, Node dependencies, and that every live suite file exists before touching the stack. It starts only the enabled local services, reads `API_URL` and `DB_URL` from `supabase status -o env`, and verifies both are on the expected loopback ports/database **before** issuing `supabase db reset --local --yes --no-seed`. It then reads only the generated local keys and runs the suites. It does not load `.env.local`, ask for keys, use a linked project, or connect to a hosted database. Query-string overrides on the PostgreSQL URL are rejected, and the PowerShell helper also uses explicit `--local` for migration up/reset. Missing Docker/CLI, a safety-check failure, or a migration failure produces a non-zero exit and an actionable `[NOT RUN]` / failure message—live tests are never silently skipped. If a preflight or target safety check fails, no test database reset has been issued.

**Destructive warning:** every `npm run test:auth-local` run resets the local database before tests; all data in the local Supabase project is erased. Do not use it with hosted keys or a production project. The fixture users/workspaces/files are cleaned up afterward; the stack remains running so you can inspect status or logs. To stop containers without intentionally deleting local volumes/data:

```powershell
.\scripts\supabase-local.ps1 -Action down
```

To manually reset (separate from the test command), use the helper's confirmation prompt:

```powershell
.\scripts\supabase-local.ps1 -Action reset
```

## If `.env.local` already exists

Do not overwrite it blindly. Run:

```powershell
supabase status -o env
```

Copy the local `API_URL` and `DB_URL`, plus `ANON_KEY` (or `PUBLISHABLE_KEY`) and `SERVICE_ROLE_KEY` (or `SECRET_KEY`), into the corresponding server-only names in `.env.local`:

```env
OKENG_ENV=development
OKENG_DATA_MODE=supabase
DATABASE_URL=<local DB_URL>
SUPABASE_URL=<local API_URL>
SUPABASE_ANON_KEY=<local ANON_KEY>
SUPABASE_SERVICE_ROLE_KEY=<local SERVICE_ROLE_KEY>
```

Keep existing application secrets, set them to development-only values of at least 32 characters, and retain exact local origins such as `http://localhost:3000` (no wildcard). Do not add any of these values to a client-side `NEXT_PUBLIC_*` variable.

## Hosted Supabase option

For a separate hosted **development** project, configure its project URL, database URL, anon key, and service-role key only in your machine's ignored `.env.local` or a secrets manager. Use a development project, not production, when running local migrations or experiments. `supabase db push` acts on the linked remote project and should only be run after confirming the target. Never send the service-role key in chat or commit it.

## What this coding session can access

There is no attached PostgreSQL server or object-storage service inside the Arena coding sandbox. This session also cannot launch the Docker stack (Docker, Supabase CLI, and `psql` are not installed here), reach your Windows machine's `localhost`, or connect to a hosted Supabase endpoint from its restricted network. A real remote key would not change those network/runtime limits, so there is no reason to share one here.

Your practical choices are:

1. Run the local stack on Windows with this guide. A local AI agent running on that same machine can use its local database and Storage endpoints, subject to whatever local file/environment permissions you grant it.
2. Use a separate hosted development Supabase project from your Windows machine or another trusted environment that has network access. Put its secrets only in that environment's secret store or ignored `.env.local`.
3. In this Arena session, continue with static code/config work or mock/in-memory tests; it cannot verify behavior against a real database or Storage service.

A purpose-built, secure network bridge would be required to make a real database available to this isolated session; none is configured here. Keep the service-role key server-only and do not send it in chat.
